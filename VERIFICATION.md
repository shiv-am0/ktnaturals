# Local verification — KT Naturals Phase 1

This is a local development/deployment-artifact verification record, not a public launch or owner acceptance. The repository started as only the build prompt and was not a Git repository; no commit or deployment was made.

## Demonstrated

- Django 5.2 app tests: 40 passed under both `DJANGO_DEBUG=true` and production-style `DJANGO_DEBUG=false` with an ephemeral test secret and allowed test host; zero Django system-check errors. The test client simulates Caddy's HTTPS proxy header; a separate test proves raw HTTP redirects to HTTPS. Coverage includes public filtering/draft isolation, available-size starting prices, server-priced signed WhatsApp quote and stale confirmation, invalid quantity/variant/price/image, publication invariants, stale edits to products/sizes/categories/settings/archive, post-commit deletion of removed/replaced public photos, staff-only routes/CSRF, POST logout, login lockout, sample-data idempotence, SEO titles/XSS-safe JSON-LD, unapproved information-page noindex, and the PDF import's row totals/idempotence/demo cleanup/owner-photo protection.
- `manage.py makemigrations --check --dry-run` — no pending model changes. `manage.py check` — no errors.
- `python -m unittest catalogue.tests.test_backups deploy.test_backup_wrapper` — 12 tests pass. WAL-consistent SQLite backup, media checksums, retention, corruption/path/symlink rejection, backup wrapper restart on failure and root-only rclone filters. `python qa/test_rclone_filters.py` — actual rclone 1.70 local-to-local copy/check succeeded, including hidden media inside completed snapshots; lock/staging excluded. No real off-server destination was contacted.
- `docker build -t ktnaturals:local-verification .` and `python qa/container_smoke.py` — built Python 3.13 image; production-mode migrations, collectstatic, Gunicorn HTTP200, SQLite persistence after container restart, and separate restored database/image content all passed in a disposable local Docker volume. No public port was permanently opened.
- `docker compose config --quiet` with non-secret invalid-domain values and Caddyfile validation in Caddy 2.10 — passed. `pip-audit -r requirements.txt` — no known vulnerabilities reported at check time. Bandit reports two `mark_safe()` warnings in `catalogue/seo.py:9`; the serialized JSON replaces `<`, `>` and `&` with Unicode escapes before marking safe, and a regression test proves `</script>` cannot terminate the data script. This is a reviewed static-scan finding, not a claim of zero security risk.
- `qa/verify_catalogue_import.py` compared every local imported product/variant with the transcribed PDF table: 18 products, 61 pack sizes, four categories, zero demo products and 18 labelled photo placeholders. `qa/check_seo.py` validated 26 local sitemap pages for unique titles, descriptions, one H1, canonical URLs, parsable JSON-LD, INR/offer prices and draft/archive exclusion. About is published from the PDF story; privacy/delivery policy pages remain draft/noindex. A pre-import SQLite+media snapshot was restored into an isolated location and its six old demo rows verified.
- `qa/browser_audit.py` with Chromium and axe-core 4.10.3: 93 page/viewport combinations at 360, 768 and 1440px; zero status, horizontal overflow, broken-image, missing-alt, JS exception or WCAG A/AA automated violations. Home/catalogue also render with JavaScript disabled. Full-page screenshots/results in `qa/evidence/` (ignored by Git).
- `qa/owner_flow.py`: browser staff login, category, draft product, two INR sizes, processed cover image, publish, successful product/price edits, public detail, responsive owner editor and archive passed. The script removes its disposable records/account/photos. Owner editor screenshots in `qa/evidence/owner/`.
- Ruff formatting check and essential E/F syntax/error checks passed. The broader default rule set also flags optional import-order, mutable class-attribute (including Django model metadata/migrations) and stylistic rules; those were not adopted as a project lint contract.
- Lighthouse 12 local mobile emulation on a development server after import: home and a catalogue product both returned performance/accessibility/SEO 100/100/100. JSON audits are in `qa/evidence/lighthouse-catalogue-home.json` and `qa/evidence/lighthouse-catalogue-product.json`. These are local synthetic results, not production mobile field data or guaranteed scores.

## What still needs real owner/operator action

- Real domain, clean product photographs and a higher-resolution original logo; owner confirmation of the PDF-sourced phone, story, product claims, availability and prices (including the conflicting Khapli 10 kg poster/table pricing); approved privacy/delivery policy, current business location and opening hours. The PDF-sourced local catalogue uses visibly labelled image placeholders and must not be deployed without review. See `CATALOGUE_IMPORT.md` for source provenance and ambiguities.
- Public VPS deployment, real DNS and ACME TLS certificate issuance, host UID and firewall validation, off-server backup credentials/transfer/retention and scheduler activation, restore of an off-server copy, real WhatsApp click-to-chat behavior on a configured number, Google Search Console ownership/sitemap submission, Google rich-results live URL validation, and production field performance have **not** been exercised. Follow `OPERATIONS.md` and `SEO_LAUNCH.md` after approval.
- Single-server SQLite and short owner edits are an intentional Phase 1 limit. Responsive image generation currently stores an optimized WebP after resizing to at most 1600px; separate multi-width srcsets are not generated. Revisit if real photo sizes/Lighthouse results warrant it. Automatic accessibility scans do not replace hands-on assistive-technology/owner usability testing.
